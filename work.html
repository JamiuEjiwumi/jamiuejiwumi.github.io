01 / PLATFORM ENGINEERINGImplemented / evolving

An organisation-wide delivery foundation

A reusable platform delivery model that standardises infrastructure building blocks and CI/CD contracts while preserving application-team ownership.

The engineering challenge

Individual applications needed consistent infrastructure and delivery patterns without coupling their Terraform state, release cadence or configuration to a central monolith.

Decisions & implementation

  • Separate platform-owned, versioned modules and reusable workflow templates from application-owned Terraform roots and state.
  • Define narrow module contracts and examples rather than force a single infrastructure blueprint.
  • Prefer short-lived GitHub-to-AWS federation, validated Terraform plans and approval-controlled deployment boundaries.
  • Design onboarding around composable patterns suitable for different AWS workloads.
OUTCOME / CURRENT POSITION

A reusable module and delivery library adopted as a foundation for application onboarding and improved standardisation.

“Keep platform standards central; keep workload state and release ownership local.”

02 / RELEASE ENGINEERINGImplemented / rollout staged

Pack Manager: controlled container releases

Moving from fragile application delivery towards immutable container images, governed environment promotion and explicit recovery paths.

The engineering challenge

Deployment processes needed stronger artifact consistency, clearer environment separation and reduced dependence on persistent cloud credentials.

Decisions & implementation

  • Produce PHP and Nginx application images in CI and publish immutable images to ECR.
  • Use explicit artifact identity for deployment and recovery rather than rebuilding on production hosts.
  • Introduce GitHub OIDC and scoped AWS roles; strengthen private-by-default infrastructure.
  • Apply Terraform validation, deployment health checks and controlled UAT / production workflows.
OUTCOME / CURRENT POSITION

Established reusable delivery and security patterns, with environment release paths implemented and validated progressively.

“Build once; know exactly what runs; preserve a tested path back.”
DockerECRTerraformGitHub OIDCGitHub Actions
03 / ENTERPRISE MODERNISATIONImplemented / production governance ongoing

CRM: safer Windows and database delivery

Modernising a legacy-compatible application delivery estate without trading speed for database or release risk.

The engineering challenge

Manual release steps across Azure-hosted Windows/IIS environments created inconsistency, while database project drift made schema deployment reports unsafe to treat as automatic approvals.

Decisions & implementation

  • Create reusable environment-aware delivery scripts and controlled release / hotfix routes.
  • Use immutable application artifacts and environment-scoped secrets and approvals.
  • Introduce database deployment reporting before schema changes; treat unexpected drops as blockers.
  • Prioritise reconciliation, backup and validation before production database promotion.
OUTCOME / CURRENT POSITION

Automated non-production deployment pathways with production controls and database drift remediation tracked separately.

“Application releases can be automated; destructive database changes must remain deliberate.”

04 / NETWORK AUTOMATIONDocumented LinkedIn project · Jan 2026

Azure Virtual WAN migration automation

An IaC-driven sandbox for recreating a multi-region Azure Virtual WAN topology across tenant boundaries.

The engineering challenge

Rebuilding a complex hybrid-network backbone needs repeatable sequencing and validation to reduce manual configuration error.

Decisions & implementation

  • Structure modular Bicep templates with regional parameter files and YAML deployment definitions.
  • Orchestrate virtual hubs, managed identities, RBAC, Fortinet NVAs, routing intent and hub connections with PowerShell.
  • Use GitHub Actions and OIDC-based Azure authentication instead of persistent deployment secrets.
  • Include canary deployment steps before broader migration changes.
OUTCOME / CURRENT POSITION

Created a reusable deployment foundation and controlled validation process for the target-tenant migration sandbox.

“Network migrations require deterministic ordering, identity boundaries and controlled validation.”

05 / AI INTEGRATION & CLOUD IDENTITYDelivered · Dev / UAT / Production

AI-powered CRM integration across Azure and AWS

Designed and delivered the cloud infrastructure and secure delivery model for an AI connector generating property descriptions for an Azure-hosted CRM application, backed by AWS APIs, Lambda and an AI provider.

The engineering challenge

Connect existing Azure CRM workloads to AWS-hosted AI services without persistent AWS keys, while preserving environment isolation, developer testing, and controlled release promotion.

Decisions & implementation

  • Built reusable Terraform configurations for AWS infrastructure, identity federation, environment isolation and deployment roles.
  • Federated Microsoft Entra ID managed identities with AWS STS for short-lived workload access; scoped IAM permissions and SigV4-signed requests to authorised API routes.
  • Enabled approved developers to test locally through interactive enterprise sign-in using MSAL and temporary credentials, with distinct Dev and UAT roles and scopes.
  • Implemented GitHub Actions routing from develop to Dev, release/* to UAT, and master to Production using GitHub OIDC.
  • Supported UAT and Production deployment, resolving Terraform state, identity, role-permission and pipeline configuration issues; documented repeatable provisioning for existing or new developer applications.
OUTCOME / CURRENT POSITION

Delivered a multi-environment integration foundation supporting secure CRM-to-AWS AI requests, controlled developer testing and repeatable release engineering through UAT and Production.

“Cross-cloud AI integration works best with short-lived identity, explicit API permissions and repeatable environment contracts.”

05 / CLOUD SECURITYAzure side configured · integration steps ongoing

Azure-to-AWS workload federation

Designing an identity bridge for Azure-hosted applications consuming protected AWS services.

The engineering challenge

Cross-cloud API access must establish who is calling, for which environment and with what scope—without shipping long-lived keys to servers.

Decisions & implementation

  • Use trusted issuer, audience and subject claims as explicit trust-policy inputs.
  • Constrain AWS role permissions to the actual workload contract and separate environments.
  • Provide verification scripts for token claims to reduce misconfigured trust relationships.
  • Test federation before enabling target API permissions.
OUTCOME / CURRENT POSITION

Prepared Azure-side federation configuration and claims verification for subsequent AWS trust integration.

“Trust the exact workload identity, not the cloud account in general.”
Azure IdentityAWS IAMOIDC / JWTPowerShell
06 / RELIABILITY ENGINEERINGInvestigation / remediation recommendations

Production incident analysis and operational resilience

Evidence-based investigation of application and infrastructure failure modes, including file descriptor exhaustion and background worker lifecycles.

The engineering challenge

Apparent infrastructure symptoms can mask process cleanup, timeout and EFS-related issues; remediation needs to distinguish confirmed findings from hypotheses.

Decisions & implementation

  • Correlate host limits, kernel events, NFS/EFS observations and application processes before assigning root cause.
  • Review browser child-process cleanup, HTTP timeouts, worker recycling and scheduled workload overlap.
  • Recommend targeted safeguards and telemetry rather than speculative changes to production.
  • Preserve an auditable RCA with proposed remediations and verification criteria.
OUTCOME / CURRENT POSITION

Documented evidenced defects, candidate contributing factors and a staged remediation/monitoring plan.

“Separate observed evidence, plausible contributors and confirmed root cause.”
LinuxPHP / NodeEFS / NFSNew RelicIncident RCA

CircleLedger: community finance SaaS

A personal product exploring transparent membership finance, dues, levies, welfare workflows, approvals and treasurer handovers.

The engineering challenge

Community associations need consistent records, transparent member statements and reliable administrative handovers.

Decisions & implementation

  • Model membership, financial obligations and receipts as auditable workflows.
  • Prioritise validation, safe imports and permission-aware administrative actions.
  • Keep the product independent of employer code and infrastructure.
  • Iterate through real user needs rather than oversized platform architecture.
OUTCOME / CURRENT POSITION

An independently developed, evolving product with a private codebase.

“Earn trust through clear records, explainable transactions and operational simplicity.”
